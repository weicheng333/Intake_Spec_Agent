# 维度分析、原话澄清与收口

开始完整澄清流程时读取；已有完整 TaskSpec 的定向修订只处理指定内容，不重走全部流程。

## 先分析，再列维度，再提问

维护本任务稳定的维度编号，例如 D01；新增维度追加编号，避免用户选择旧编号时对应内容变化。
每项列出：编号、维度、当前描述及确定程度、缺口或含糊原话、必要/可选、丰富建议、推荐理由和影响。
确定程度区分“用户已明确”“有描述待核验”“暂定假设”“尚未涉及”。“描述完整”不等于用户已确认最终方案。
已经足够明确的维度注明“不建议重复补充”及原因，不为每一项制造新问题。

维度依据本项目筛选：例如工具的触发与人工边界、多人系统的角色与权限、数据产品的来源与质量、迁移项目的兼容与回退；不要固定套用所有标签。
新增信息改变相关性时，说明新增维度及原因。一个歧义涉及多个维度时合并提问，列出关联维度而不是重复问。

## 用户已经说了，但没有说清楚

识别可能影响实施的含糊词、指代、隐含前提、范围边界和无法测量的标准；不能只查用户没说什么。

例如“做一个简单、安全、能自动处理的工具”：

- “简单”：操作步骤少，还是功能范围小？对应用户体验/范围。
- “安全”：保护数据、限制权限，还是避免误操作？对应安全/权限/异常。
- “自动处理”：什么触发、自动完成哪些步骤、哪些需人工确认？对应流程/自动化边界。

提问时引用用户原话 → 说明不清晰处及答案影响 → 标注维度 → 提供选项和推荐理由。
推荐不能作为默认选中后的用户事实；允许用户自述、组合必要条件或纠正选项。无法互斥的选项应重新组织，不强迫单选互补要求。
“每天晚上8点提醒一次”等已经明确且与其他要求不冲突的描述，直接记录，不再问频率。
主观修辞只有影响范围、成本、权限或验收时才值得澄清，不把每一句话拆成问题。

## 展示方式故障不改变澄清合同

提问遵循入口的“提问展示与分组”：问题内容、展示渠道和每轮数量分别决定，不能混为一谈。
普通文字选项优先，让用户手动输入答案；不设置作答倒计时，不因暂未回复就替用户决定。只有明确要求弹窗时才考虑切换渠道，仍须遵守宿主规则。文字发出后结束本轮等待回复，避免用持续等待工具占住会话。
例如用户只要求停用弹窗时，保留当前维度和待回答内容；不推断用户要求逐题，也不把选项推荐从需求方法中删除。
适用宿主禁止文字多选时，应解释无法按原样呈现的原因，使用允许的开放问题；工具参数有选项不代表文字中已显示选项。
用户只回答一组中的部分问题时，记录明确答案，下轮只处理剩余项及受影响的新问题，不把推荐项补成未回答的答案。

## 继续完善的决策点

先简述已完善维度及每项成果，再按优先级列出可丰富方向、价值和影响；由用户选择维度编号继续。
推荐基于当前方案，不机械推荐继续：

- 必要信息仍有缺口：说明阻塞原因，继续必要澄清。用户坚持停止时可展示未完成清单，但不能宣称就绪或 READY。
- 必要信息齐全、仍有明显高价值可选项：建议继续，并说明是可选，不扩大范围。
- 必要信息齐全、其他项不影响本次目标：建议停止并进入清单核验，不追求无限完善。

选择“继续”但未指定维度时，给二至三个最相关方向；尚无实质变化不增加版本、不写入。
选择“全部采用”时，以本轮明确展示的建议为范围，检查互斥和依赖，不扩展到未展示建议。
“好的”等不能区分继续/停止/确认的回复，先澄清意图。

## 停止后展示的当前需求清单

清单是用户需求，不是实施 DAG；完整列出，不只展示本轮修改。

1. 目标与成功定义。
2. 用户、角色、使用场景。
3. 范围、非范围和主要流程。
4. 数据、权限、安全及相关约束。
5. 交付物与逐项可验证验收标准。
6. 异常处理、风险、依赖、预算与截止日期（未知时明确未设置）。
7. 已完善维度及成果、剩余假设、非阻塞未知项、跳过或未采纳的可选建议。
8. 关键决定、交接边界；若修改过，列出新增/修改/受影响的验收项。
9. 校验后展示当前受审 revision/version 和真实 checksum、明确的核验请求及保存情况。

按项目相关性合并条目，但不能隐藏必要缺口。没有预算或截止日期保持 null，不自行补数字。
第一次展示未校验清单时不要生成假 checksum；若可在本轮完成真实校验，直接展示校验后的完整清单，避免重复长文。
“不需要继续完善”只结束补充；用户未看到最终清单就说“确认”，不能作为对未展示版本的确认。
仅明确确认已展示的当前 revision/checksum 才走现有保存门；实质修改后重新核验，旧确认不沿用。
已 READY 的旧方案可作为完善基线；未修改前保留原定稿，新草稿不得继承 READY。
